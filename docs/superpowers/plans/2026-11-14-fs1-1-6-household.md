# FS-1 1.6 — `household`: rencana implementasi

> **Untuk agen pelaksana:** SUB-SKILL WAJIB: superpowers:subagent-driven-development (disarankan) atau superpowers:executing-plans. Langkah memakai kotak centang (`- [ ]`).

**Tujuan:** modul `household` di server dan kontraknya: pemberitahuan pengelola server berversi per akun dengan tahan tulis `NOTICE_UNREAD` sampai versi terbaru diakui (SEC-34), membuat rumah tangga dengan kelima konsep 06 §3.1 ditulis terpisah, undangan F01 sampai F05 dengan F04 oleh pengundang, keanggotaan dan pemeriksaan pemilih rumah tangga, serta jalur pendaftaran (a) lewat token undangan (SEC-158), sehingga dua akun uji dapat bergabung ke satu rumah tangga lewat undangan lewat API (kriteria selesai langkah 1; layarnya di 1.10).

**Arsitektur:** paket domain baru `internal/household` (logika, kueri sqlc di `internal/household/householddb`) dan layanan Connect `casa.v1.HouseholdService` yang handler-nya di `internal/api`. Modul tidak saling mengimpor: lapisan API menyusun `household` dan `identity` di dalam satu transaksi `command.Run` bila sebuah perintah menyentuh keduanya (09.2 §1 "Modul lain memanggilnya lewat fungsi Go di dalam transaksi yang sama"; Q10). Interseptor batas 1.3/1.4/1.5 mendapat satu langkah baru: tahan `NOTICE_UNREAD` untuk setiap perintah tulis yang bukan `notice_exempt` (09.3 §1). `identity` mendapat sumber undangan pada `StartSignUp`/`CompleteSignUp` (carry-over 1.4 Q8) dan beberapa fungsi ekspor kecil untuk lapisan API. Setiap tugas fitur adalah potongan vertikal: migrasi atau kontrak, modul, handler, dan uji tingkat API terhadap PostgreSQL 18 nyata.

**Stack:** Go (toolchain di `server/go.mod`), pgx v5, goose v3, sqlc (biner yang sudah dipatok), connect-go v2, protovalidate, stdlib `time/tzdata`. **Tanpa dependensi baru** di Go maupun npm (Q17: pustaka uji properti ditunda ke 1.7).

**Spesifikasi:** 14 §3.3 langkah 1 (kolom server, butir `household`; kolom "Selesai bila"); 05 `FAM.md` FR-FAM-001 (AC-1 sampai AC-10), FR-FAM-003 (AC-1 sampai AC-7), FR-FAM-004 (AC-1 sampai AC-12, AC-14 bagian server), FR-FAM-006 (AC-2, AC-3), FR-FAM-019 (AC-1 sampai AC-3, AC-8, AC-10, AC-11 bagian server), FR-FAM-020 (AC-1 sampai AC-4, AC-6); 06 §2.4, §2.5, §3.1, §3.5, §3.6 (F01 sampai F05), INV-A01, INV-A13, INV-A48 (a) sampai (c), N-24, N-25; 09.2 §1, §3 (lapis 1 sampai 4, "Tabel global", "Kebocoran lewat unique check", `full_adult_members`), §4, §5.1, §6, §8, §9, §10; 09.3 §1 (`NOTICE_UNREAD`, tabel jenis perintah, FAM online-first); 09.4 §2 baris "Batas laju", "Undangan", "Pendaftaran tertutup"; 10.1 §5.1 (aturan 1 sampai 7), §8.1 baris "Pemakaian token", SEC-05, SEC-10, SEC-12, SEC-28 sampai SEC-35, SEC-38 (a), (b), (c), (e), SEC-39 (a), (b), §11.3; 10.3 SEC-80, SEC-109 (a); 10.4 SEC-158; 10.5 SEC-171 (b) (3), SEC-175 (c), SEC-178 (a), (b); ADR-005, ADR-013, ADR-014, ADR-016, ADR-017, ADR-028 butir 3, ADR-030; glosarium ("Keanggotaan", "Undangan", "Pemilik rumah tangga", "Preset dua dewasa setara", "Anggota dewasa penuh", "Pemberitahuan pengelola server", "Tahan tulis per akun", "Jejak keamanan", "Pendaftaran tertutup"); rencana 1.2 (gerbang katalog), 1.3 (`NOTICE_UNREAD` sebagai perilaku di 1.6), 1.4 (keputusan 1, "Yang sengaja tidak", Q8, putusan Q8), 1.5; `_progress.md` "FS-1 1.4 selesai", "FS-1 1.5 selesai"; `ENGINEERING-STANDARDS.md` §1 sampai §9.

## Keputusan yang diambil rencana ini

Butir bertanda **(Qn)** memakai rekomendasi rencana sambil menunggu putusan lead atas Qn di akhir. Bila lead memutus lain, yang berubah disebut di pertanyaannya.

1. **Cakupan F01 sampai F05 saja (Q11).** Keluar, masa tenggang, dan pembatalannya (F06 sampai F08, FR-FAM-012) memerlukan `exit_closure` dan buku pribadi (ledger) dan dibangun bersama FR-FAM-012 sesudah langkah 2. Karena itu `membership` belum punya kolom state: baris ada = aktif; F06 menambah kolom `state` dengan bawaan `'active'` (expand). Guard F01 "tidak ada anggota dalam `keluar_tenggang`" benar dengan sendirinya sampai F06 ada; komentar di kode menunjuk FR-FAM-003/AC-7.
2. **Tabel dan pemiliknya (Q1).** Migrasi `00005_household.sql` membuat, semuanya milik modul `household`:

   ```sql
   household (id uuid PK DEFAULT gen_random_uuid(), name text NOT NULL, time_zone text NOT NULL,
              currency char(3) NOT NULL DEFAULT 'IDR' REFERENCES currency (code),
              income_source_market text NOT NULL DEFAULT 'ID' CHECK (income_source_market IN ('ID')),
              version bigint NOT NULL DEFAULT 0, created_at timestamptz NOT NULL,
              UNIQUE (id, currency))                                    -- 09.2 §5.1; 06 §2.4; 07 §2.1, §3.1
   membership (household_id uuid NOT NULL REFERENCES household (id), member_id uuid NOT NULL DEFAULT gen_random_uuid(),
               account_id uuid NULL,             -- pemetaan identitas anggota (07 §8.2): dapat diputus; tanpa FK ke account (SEC-02 gerbang kunci)
               display_name text NULL,           -- FR-FAM-006; ikut diputus bersama account_id
               role text NOT NULL CHECK (role IN ('household_owner')),
               permission_set text NOT NULL CHECK (permission_set IN ('two_equal_adults')),
               joined_at timestamptz NOT NULL,
               PRIMARY KEY (household_id, member_id), UNIQUE (household_id, account_id))
   CREATE INDEX membership_account ON membership (account_id);          -- ListMemberships, pemeriksaan pemilih
   approval_authority (household_id, member_id, request_type text NOT NULL CHECK (request_type IN ('all')),
                       limit_amount bigint NULL, valid_from timestamptz NOT NULL, valid_until timestamptz NULL,
                       PRIMARY KEY (household_id, member_id, request_type, valid_from),
                       FOREIGN KEY (household_id, member_id) REFERENCES membership)        -- 06 §3.1
   household_rule (household_id, version int NOT NULL, preset_id text NOT NULL CHECK (preset_id IN ('two_equal_adults')),
                   request_threshold bigint NULL, currency char(3) NOT NULL,
                   agreement_mode text NOT NULL DEFAULT 'all' CHECK (agreement_mode IN ('all')),
                   created_at timestamptz NOT NULL, PRIMARY KEY (household_id, version),
                   FOREIGN KEY (household_id, currency) REFERENCES household (id, currency))  -- 06 §3.1; 09.2 §7
   relationship (household_id, member_id, other_member_id, kind text NOT NULL,
                 PRIMARY KEY (household_id, member_id, other_member_id), FKs ke membership)  -- tidak ada baris di pilot
   object_event (household_id, object_kind text NOT NULL CHECK (object_kind IN ('household','invitation')),
                 object_id uuid NOT NULL, seq bigint NOT NULL,
                 actor_kind text NOT NULL CHECK (actor_kind IN ('member','invitee','system')),
                 actor uuid NULL,                 -- member_id; invitee: NULL; system: NULL
                 rule text NULL,                  -- system: rule id (INV-A01), mis. 'invitation.expired'
                 command text NOT NULL, from_state text NULL, to_state text NOT NULL,
                 idempotency_key uuid NULL, server_time timestamptz NOT NULL,
                 PRIMARY KEY (household_id, object_kind, object_id, seq))  -- 09.2 §5.1; 06 §2.5, S-5 (Q14)
   ```

   `approval_mode` 06 §3.1 tidak dibuat karena tidak ada nilai lain di pilot dan tidak ada aturan yang membacanya sebelum `request` (langkah 4); `request` menambahnya (expand) bersama `resolve_approvers`. `responsibility` dibuat bersama tagihan berulang (langkah 3), karena subjeknya belum ada; FR-FAM-001/AC-2 tidak menyebutnya. Hak `app_rw`: `SELECT, INSERT` pada semua; `UPDATE (name, time_zone, version)` pada `household` (rename dan zona waktu belum dibangun: hanya `version`, kolom lain ditambah tugasnya); `object_event` tambah-saja (FR-FAM-020/AC-6; SEC-39 (a)); tanpa `DELETE` di mana pun. `job_runner`, `lifecycle_rw` tanpa hak.
3. **Kebijakan RLS (Q2).** Tabel rumah tangga memakai kebijakan lapis 4 persis (`householdPolicy` gerbang katalog), kecuali tiga yang dinyatakan di katalog dengan sumbernya:

   | Tabel | `USING` | `WITH CHECK` | Alasan |
   |---|---|---|---|
   | `household` | `id = H` | `id = H` | kolom kuncinya `id` (09.2 §5.1) |
   | `membership` | `household_id = H′ OR account_id = A` | `household_id = H′` | `ListMemberships` dan pemeriksaan pemilih mencari keanggotaan akun sendiri sebelum rumah tangga diketahui (SEC-38 (a)) |
   | `invitation` | `household_id = H′ OR token_hash = T` | `household_id = H′` | penerima menemukan undangan dari token sebelum rumah tangga diketahui (SEC-28) |

   `H` = `current_setting('app.household_id')::uuid` (tanpa `missing_ok`, 09.2 §3 lapis 4); `H′` = `nullif(current_setting('app.household_id', true), '')::uuid`, karena dalam transaksi pencarian `app.household_id` bernilai `''` dan cast tanpa `nullif` gagal (temuan 1.2). Klausa pencarian hanya di `USING` (10.1 §5.1 aturan 1, 7).
4. **Urutan pemeriksaan pemilih** (09.2 §3 lapis 1; SEC-38 (a)): `household_id` di permintaan hanya pemilih. Handler memanggil `household.Member(ctx, account, selector)` dalam `Read(Scope{AccountID})` (lewat klausa `account_id = A`); tidak ada → `ErrNotFound`, dijawab sama dengan rumah tangga yang tidak ada (SEC-05; FR-FAM-020/AC-1, AC-4). Sesudah lolos, perintah berjalan dengan `Scope{HouseholdID: selector, AccountID}` dan memeriksa ulang keanggotaan di dalam transaksi (otorisasi ulang saat tiba, SEC-151; 09.2 §6 langkah 2).
5. **Perintah tingkat akun memakai `scope_id = account_id`** (09.2 §8) walau transaksinya membawa rumah tangga: `CreateHousehold` (rumah tangga baru) dan `AcceptInvitation` (rumah tangga pengundang). `command.Run` memilih `HouseholdID` lebih dulu, jadi `command` mendapat `RunForAccount` dan `StoredForAccount` dengan aturan yang sama dan `scope_id = scope.AccountID`. Perubahan ini satu tugas tersendiri, Tugas 2 (refaktor terpisah dari perilaku, ES §7).
6. **Pemberitahuan pengelola (Q3, Q4).** Versi teks adalah data produk yang terbit bersama build (SEC-35: versi terbit bersama atau sebelum build fiturnya), ditulis oleh migrasi seperti baris `IDR` di `00001`: tabel `operator_notice (variant, version, title, paragraphs text[], features text[], PRIMARY KEY (variant, version), CHECK (cardinality(paragraphs) = cardinality(features)))`, `variant IN ('couple','family','general')`, hanya `SELECT` bagi `app_rw`, kebijakan `USING (true)` seperti `currency`. `{pengelola}` diisi saat ditampilkan dari kredensial `operator-name` (`casa serve`), sehingga nama orang tidak masuk repositori. Per akun: `operator_notice_ack (account_id, variant, version, text_sha256 bytea, issued_at, acknowledged_at NULL, PRIMARY KEY (account_id, variant, version, text_sha256))`, tabel global berkebijakan akun, `SELECT, INSERT, UPDATE (acknowledged_at)`. Identitas sebuah versi bagi akun = (varian, nomor, SHA-256 teks yang sudah diisi), sehingga mengganti nama pengelola juga menahan sampai dibaca ulang (SEC-34 "versi baru meminta pembacaan ulang").
   - **Varian akun:** di 1.6 semua akun `couple`, satu konstanta `pilotNoticeVariant` dengan komentar `ponytail:` yang menunjuk FR-FAM-019/AC-9 (Tier 3, sebelum GR-4) untuk pilihan per akun.
   - **Terbit saat pertama terlihat:** pada pemeriksaan tahan atau `GetOperatorNotice`, bila versi terbaru varian akun belum punya baris, satu transaksi menulis barisnya (`issued_at`) dan satu `security_event` `notice_version` (detail `<variant>:<version>`) untuk akun itu saja. Tidak ada tulisan lintas akun dan tidak ada job; akun tidak dapat ditahan sebelum ia menghubungi server, jadi waktunya sama dari sisi pemilik akun.
   - **Tahan:** akun ditahan bila baris versi terbaru tidak `acknowledged_at`. Hanya pengakuan atas versi terbaru yang melepas; pengakuan atas versi lain ditolak `STATE_CHANGED` tanpa tulisan, dan klien membaca ulang (09.3 §1 "v4 terbit sebelum v3 diakui").
   - **Pengakuan:** perintah `AcknowledgeOperatorNotice` (`hold_seconds: 0`, `notice_exempt: true`; masuk `noticeExemptNotProtective`), mengisi `acknowledged_at` dan menulis `security_event` `notice_acknowledged` (glosarium "Jejak keamanan"). Riwayat versi lama tetap (FR-FAM-019/AC-3). `security_event.kind` diperluas di `00007`.
   - **v1 `couple`** berisi teks 10.1 §11.3 dengan kata-kata 08 §7.5, tanpa paragraf **[Tier 2]** (SEC-35: fitur belum dibangun) dan dengan paragraf **[Klien web]** (SEC-178 (b)); `features` semua `''`. Medan `feature` per paragraf ada di kontrak sejak v1 agar build pertama sudah tahu menandai "berlaku saat fitur ini tersedia" (FR-FAM-019/AC-8).
7. **Langkah tahan di batas (Q3).** `api.NewServer` mendapat parameter `noticeHeld func(context.Context, pgtype.UUID) (bool, error)`. Langkah baru **6a**, sesudah versi minimum dan sebelum kunci idempotensi: perintah tulis yang tidak `notice_exempt` dari akun yang ditahan → `CodeFailedPrecondition` dengan `ERROR_CODE_NOTICE_UNREAD` (sudah ada), sebelum isi divalidasi penuh, sehingga perintah antrean lama tidak berubah menjadi `invalid_argument` dan tidak tercatat di `idempotency_record` (09.3 §1 "menunda, tidak menolak"). RPC `identity` dan bacaan tidak pernah lewat langkah ini. Urutan 09.3 §1 butir 1 sampai 3 (`WRITE_FROZEN` sebelum `NOTICE_UNREAD`) dipenuhi saat tahan tulis seluruh server dibangun (ADR-028 butir 3); komentar di langkah 6a menyebut tempatnya. Pemeriksaan berjalan di transaksinya sendiri; perintah yang sedang terbang tepat saat versi baru terbit dapat lolos sekali **[Usulan]**.
8. **Membuat rumah tangga (Q5, Q6).** `CreateHousehold` (perintah tingkat akun, `hold_seconds: 0`, online-first 09.3 §1): isian `name` (1 sampai 60 karakter sesudah dipangkas, satu baris), `time_zone` (nama IANA, diperiksa `time.LoadLocation`; `cmd/casa` mengimpor `time/tzdata`), `display_name` (1 sampai 40 karakter, satu baris), `age_declaration_version` (SEC-80). Ditolak bila akun dibuat lewat undangan atau sudah anggota rumah tangga mana pun (FR-FAM-001 "Aktor", AC-5, AC-10 bagian akhir) dengan `HOUSEHOLD_CREATION_NOT_ALLOWED`. Dalam satu transaksi: `household` (IDR, pasar `ID`, FR-FAM-001/AC-7), `membership` (`household_owner`, `two_equal_adults`), satu `approval_authority` (`all`, tanpa batas, tanpa akhir), `household_rule` versi 1 (`two_equal_adults`, ambang NULL, `agreement_mode 'all'`), tanpa baris `relationship` (FR-FAM-001/AC-2), satu `object_event` `household.created`, dan `consent_record` usia bila belum ada. Hari mulai periode (AC-1) dan ganti mata uang (AC-8) **tidak** di 1.6 (Q5).
9. **Pernyataan usia (Q6).** Tabel global `consent_record (account_id, kind text CHECK (kind IN ('adult_age')), text_version int, recorded_at, PRIMARY KEY (account_id, kind, text_version))`, kebijakan akun, `SELECT, INSERT`. `CreateHousehold` dan `AcceptInvitation` membawa `uint32 age_declaration_version`: akun tanpa baris dan medan bukan versi teks saat ini (`currentAgeDeclarationVersion = 1`) → `AGE_DECLARATION_REQUIRED` tanpa efek; medan = versi saat ini → baris ditulis di transaksi yang sama (SEC-80, SEC-32; FR-FAM-004/AC-12). Akun yang sudah punya baris tidak perlu medan.
10. **Token undangan (Q7).** `CreateInvitation` (perintah, F01) membuat undangan tanpa token dan menjawab `invitation_id`, `expires_at`; token tidak pernah masuk `idempotency_record` (keputusan 8 rencana 1.4). `IssueInvitationLink` (RPC daring di luar tabel jenis perintah, seperti `Reauthenticate`) membuat token baru 32 byte untuk undangan terbuka milik pemanggil yang belum diterima, menggantikan `token_hash` lama (tautan lama mati), dan menjawab token sekali. Dengan begitu FR-FAM-003/AC-2 ("menampilkan undangan yang sudah ada") terpenuhi: klien menampilkan undangan yang ada dan dapat meminta tautan baru. Tautan web `<origin>/invite#<token>` (SEC-175 (c)); teks yang dibagikan dibuat klien dan hanya memuat tautan (SEC-29). Umur 7 hari dari F01 (SEC-28).
11. **Undangan sebagai state machine** (06 §3.6): `invitation (household_id, id, inviter uuid NOT NULL, token_hash bytea NULL, state text CHECK (state IN ('open','accepted','confirmed','cancelled','rejected','withdrawn','expired')), invitee_account_id uuid NULL, invitee_display_name text NULL, created_at, expires_at, closed_at NULL, version bigint NOT NULL DEFAULT 0, PRIMARY KEY (household_id, id), FOREIGN KEY (household_id, inviter) REFERENCES membership)`; indeks `invitation_token ON invitation (token_hash) WHERE token_hash IS NOT NULL` (bukan unik, karena kunci unik harus diawali `household_id`; 256 bit acak) dan `invitation_live ON invitation (household_id) WHERE state IN ('open','accepted')` **UNIQUE** ("tidak ada undangan lain yang belum gugur"). `app_rw`: `SELECT, INSERT, UPDATE (token_hash, state, invitee_account_id, invitee_display_name, closed_at, version)`. Setiap transisi = compare-and-set atas `version` (09.2 §9) + satu `object_event`.
12. **Kedaluwarsa dihitung, lalu ditulis oleh perintah berikutnya (Q8).** Undangan `open`/`accepted` dengan `now ≥ expires_at` diperlakukan gugur di setiap jalur baca dan perintah. Perintah berikutnya atas rumah tangga itu (F01 sampai F05) lebih dulu menulis transisi `expired` dengan `actor_kind 'system'`, `rule 'invitation.expired'` (F03, F05 "(waktu)"; INV-A48 (b): tidak pernah menuju aktif). Tanpa job di 1.6.
13. **F02 `AcceptInvitation`** (perintah tingkat akun): token (atau sumber pendaftaran, keputusan 15) → undangan `open`, belum lewat, penerima belum anggota rumah tangga itu, `full_adult_members < 2` (FR-FAM-004/AC-8) → `accepted` dengan `invitee_account_id`, `invitee_display_name`, `token_hash = NULL` (sekali pakai, SEC-28). Setiap kegagalan token (tidak ada, cacat, dibatalkan, lewat, terpakai, penerima sudah anggota, rumah tangga penuh) → satu penolakan `TOKEN_REJECTED` yang identik byte demi byte dengan penolakan pendaftaran (SEC-30; FR-FAM-003/AC-3 "tanpa menyebut nama rumah tangga"). Batas laju: pembatas `tokenUse` `identity` yang sama (10.1 §8.1 baris "Pemakaian token"), lewat `identity.Service.TokenUseAttempt`. Transaksi menulis dengan `Scope{HouseholdID: undangan.household_id, AccountID}`: token adalah haknya (Q2). Akun yang anggota rumah tangga lain boleh menerima (SEC-38 (c); Q18).
14. **F04/F05.** `ConfirmInvitee` (hanya pengundang; `accepted`, belum lewat) → `confirmed` dan `membership` + `approval_authority` yang identik dengan pengundang (06 §3.1; FR-FAM-004/AC-4); `RejectInvitee` (hanya pengundang) → `rejected`; `WithdrawAcceptance` (hanya penerima, tingkat akun) → `withdrawn`; `CancelInvitation` (anggota dewasa mana pun, `open`) → `cancelled` (FR-FAM-003 "dapat dibatalkan pengundangnya"; Q19). Pelaku lain → `ErrNotFound` (tidak membuka keberadaan). Tidak ada perintah lain yang menulis `membership` (INV-A48 (a), (b)).
15. **Pendaftaran lewat undangan (Q9).** `StartSignUpRequest` mendapat `string invitation_token = 4 [debug_redact = true]` tanpa aturan; tepat satu dari `setup_token` dan `invitation_token` terisi, selain itu `TOKEN_REJECTED` seragam. Email bebas (SEC-31: undangan tidak terikat email), tetap ditolak seragam bila sudah punya akun (sama dengan 1.4). `signup_verification` (identity) diperluas di `00008`: `source IN ('setup_token','invitation')`, kolom `invitation_token_hash bytea NULL UNIQUE`, `account_id uuid NULL` (diisi saat akun lahir), CHECK sumber ⇔ tepat satu hash; kebijakan `USING (token_hash = T OR setup_token_hash = T OR invitation_token_hash = T OR account_id = A)`, `WITH CHECK (setup_token_hash = T OR invitation_token_hash = T)` (10.1 §5.1 catatan 1.6), `UPDATE (token_hash, expires_at, used_at, account_id)`. Validitas undangan diperiksa lapisan API lewat `household.InvitationOpen` sebelum `StartSignUp` dan sebelum `CompleteSignUp`; akun lahir dengan `signup_via 'invitation'`. Satu akun per token undangan; tautan baru (`IssueInvitationLink`) membuka satu pendaftaran lagi. Akun undangan meneruskan F02 tanpa menempel token lagi (`from_signup`), karena tautan verifikasi dibuka di tab lain dan token sudah dibuang (SEC-171 (b) (2), SEC-175 (c)).
16. **Bacaan sebelum 1.7 (Q12).** `HouseholdService` memuat empat RPC baca daring, semuanya bersesi dan di luar tabel jenis perintah: `GetOperatorNotice`, `ListMemberships` (rumah tangga akun ini: id, nama, `member_id`, dan anggota lain dengan nama tampilan), `GetOpenInvitation(household_id)` (state, `expires_at`; saat `accepted`: nama tampilan dan email terverifikasi penerima, SEC-31), `PreviewInvitation(token | from_signup)` (nama rumah tangga, nama tampilan pengundang, `former_member_notice` selalu `false` sampai F06 ada; FR-FAM-004/AC-1, AC-10). Email penerima dibaca lapisan API lewat `identity.AccountEmail(ctx, invitee)` dalam `Read(Scope{AccountID: invitee})` yang hanya memilih `email`, sesudah `household` memastikan pemanggil pengundang undangan `accepted` itu; email tidak tersimpan di data rumah tangga (FR-FAM-004/AC-2; Q2).
17. **Kode galat baru (Q13)**, satu fungsi pemetaan `householdError` di `internal/api`:
